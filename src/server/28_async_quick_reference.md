# リファレンス：非同期クロージャ／Future

さまざまな種類の非同期クロージャとFutureを紹介してきたため、それぞれが異なるcontextのどこで、いつ実行されるのかを把握しにくくなっているかもしれません。次の表は、これまでに紹介した各種の非同期クロージャについて、コードがいつ、どこで実行されるかを簡潔にまとめたものです。それぞれがサーバーとクライアントで実行されるときに、関連する実行段階（SSR／ハイドレーション／CSR）に応じて異なる挙動をする点に注目してください。

|      | サーバーサイドレンダリング | ハイドレーション中（CSRの準備） | クライアントサイドレンダリング |
|------|-----------------------|--------------------------------------|-----------------------|
| Server function（サーバー） | 通常の非同期関数として呼び出され、本体に定義されたコードが直接実行され、結果が呼び出し元へ返されます。コンポーネント内で実行される場合は、リアクティブcontext全体にアクセスできます。 | - | （server functionの独立したエンドポイントへのHTTPリクエストに応答することで呼び出され、シリアライズされた結果がレスポンスになります。このエンドポイントは完全に独立しているため、通常リアクティブcontextは利用できません。） |
| Server function（クライアント） | - | 実行されません。（Resource型の非同期クロージャ内で定義されている場合。） | server functionのエンドポイントへHTTPリクエストを送り、レスポンス本文をデシリアライズして結果にします。関数本体のコードがクライアントへコンパイルされることはありません。 |
| Resource（サーバー） | 非同期executorにより、可能な場合は非同期クロージャが*並列*に実行されます。結果は `<script>` タグ内にエンコードされ、レスポンス本文へ含まれます。 | - | - |
| Resource（クライアント） | - | 実行されません。レスポンス本文内の `<script>` タグが結果を提供します。 | 新しい結果を返す必要が生じるたび、リアクティブシステムによって非同期クロージャが実行されます。 |
| Local Resource（クライアントのみ） | - | 実行されません。（初期値を提供するため、ハイドレーション後に一度実行されます。） | 新しい結果を返す必要が生じるたび、リアクティブシステムによって非同期クロージャが実行されます。 |
| Suspend（サーバー） | 非同期executorにより、可能な場合はこれらのFutureが*並列*に実行されます。選択した `SsrMode` により、1）Futureがpollされる方法とタイミング、2）出力ストリームの順序が変わることがあります。 | - | - |
| Suspend（クライアント） | - | ハイドレーションの一部として、これらのFutureがクライアントでもう一度最後まで実行されます。返された `view! {}` はHTMLのハイドレートに使われます。 | リアクティブシステムが必要とするたびに実行され、返された `view! {}` は定義された位置にレンダリングされます。 |

覚えておくと役立つのは、サーバーとクライアントにまたがって、最大3つの異なる実行段階があることです。その結果、ResourceやSuspend内に副作用があると、ハイドレーションのバグや予期しないプログラムの挙動が生じる可能性があります。異なる実行段階では、副作用が期待した時点や同じ順序で実行されるとは限らず、この不一致がハイドレーションエラーにつながることがあります。

たとえば、signalを設定するResourceから副作用が生じることがあります。そのResourceの非同期クロージャが、非同期に取得した値をリアクティブsignalへ渡すとしましょう。SSRとCSRでは問題なく動作しますが、ハイドレーションが関わると期待どおりには動きません。ハイドレーション中は非同期クロージャの本体が実行_されない_ため、signalも設定されません。一方、SSRではクロージャが実行されてsignalが設定されるので、この不一致がハイドレーションエラーにつながる可能性があります。これを修正するには、Resourceから値を返し、Suspendがその値を `.await` してからリアクティブsignalへ渡すようにします。これにより、3つすべての実行段階でsignalが設定されます。

単一のsignalを複数のSuspendが使う場合にも、この不一致が起こることがあります。サーバーとクライアントでは異なる非同期executorが使われるため、Suspendがpollされる順序も異なる可能性があります。実質的に実行順序が不安定になり、値がsignalへ渡される順序も変化します。最終的にはSSRとハイドレーションで値が一致しない可能性が生じ、この場合のハイドレーションエラーは非決定的になり、原因を絞り込みにくいこともあります。

もう1つの例として、SSR中のserver functionは、アプリケーションのレンダリング中に通常の非同期関数として呼び出されるため、アプリケーションが設定したすべてのcontextにアクセスできます。一方、対応するAPIエンドポイントは、はるかに単純な独立したエンドポイントハンドラーとして存在するため、アプリケーションが設定したcontextなしで動きます。したがって、アプリケーションが設定する型に対して `expect_context` や `use_context` を使っても、その値を `.leptos_routes_with_context()` でcontextへ提供していない限り動作しません。

以上は、一般的にドキュメント化された構成（つまりserver functionはResource内でのみ呼び出してawaitし、ResourceはSuspend内でのみawaitする構成）における各種の挙動を手早く参照するための例にすぎません。これらの非同期クロージャを別の方法で組み合わせたりネストしたりすると、ほかの挙動が生じる可能性があります。
