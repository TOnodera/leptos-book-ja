# ハイドレーションのバグ（と、その避け方）

## 思考実験

直感を試す実験をしてみましょう。`cargo-leptos` でサーバーレンダリングしているアプリを開いてください。（これまで例を試すのに `trunk` だけを使っていたなら、この演習のために [`cargo-leptos` のテンプレートをclone](./21_cargo_leptos.md)してください。）

ルートコンポーネントのどこかにログを置きます。（私は通常 `<App/>` と呼びますが、名前は何でも構いません。）

```rust
#[component]
pub fn App() -> impl IntoView {
	logging::log!("どこで実行される？");
	// ... その他の処理
}
```

それでは起動しましょう。

```bash
cargo leptos watch
```

`どこで実行される？` はどこに記録されると思いますか？

- サーバーを実行しているコマンドライン？
- ページを読み込んだときのブラウザコンソール？
- どちらにも出ない？
- 両方？

試してみてください。

...

...

...

では、ここから先はネタバレです。

すべてが計画どおりなら、もちろん両方に記録されます。実際、サーバーでは2回記録されます。最初はサーバーの初回起動時で、Leptosがルートツリーを抽出するためにアプリを一度レンダリングしたときです。2回目はリクエストを送ったときです。ページを再読み込みするたび、`どこで実行される？` はサーバーで1回、クライアントで1回記録されるはずです。

直前のいくつかの節の説明を考えれば、納得できるでしょう。アプリケーションはまずサーバーで一度実行され、そこでHTMLのツリーを構築してクライアントへ送ります。この最初のレンダリング中に、`どこで実行される？` がサーバーで記録されます。

WASMバイナリがブラウザに読み込まれると、アプリケーションは2回目の実行を開始します。同じユーザーインターフェイスのツリーをたどり、対話性を追加します。

> 無駄に聞こえますか？ ある意味では無駄です。しかし、この無駄を減らすのは本当に難しい問題です。Qwikのような一部のJSフレームワークはその解決を目指していますが、ほかの手法と比べて総合的な性能向上になるかどうかを判断するには、まだ早すぎるでしょう。

## バグが生じる可能性

ここまでは理解できたでしょうか。では、この章の題名「ハイドレーションのバグ（と、その避け方）」と何の関係があるのでしょう？

アプリケーションはサーバーとクライアントの両方で実行される必要があることを思い出してください。そのため、避け方を知っておくべき問題がいくつか生じます。

### サーバーとクライアントのコードの不一致

サーバーから送られるHTMLとクライアントでレンダリングされるものを一致させないと、バグを作り込むことになります。意図せずこれを起こすのは実際にはかなり難しいと思います（少なくとも、寄せられるバグ報告を見る限りでは）。しかし、次のようなコードを書いたとしましょう。

```rust
#[component]
pub fn App() -> impl IntoView {
    let data = if cfg!(target_arch = "wasm32") {
        vec![0, 1, 2]
    } else {
        vec![]
    };
    data.into_iter()
        .map(|value| view! { <span>{value}</span> })
        .collect_view()
}
```

つまり、WASM向けにコンパイルされる場合は3つの項目があり、それ以外では空になります。

ブラウザでページを読み込むと、何も表示されません。コンソールを開くとpanicが見つかります。

```
ssr_modes.js:423 panicked at /.../tachys/src/html/element/mod.rs:352:14:
called `Option::unwrap()` on a `None` value
```

ブラウザで動くアプリのWASM版は、要素（実際には3つの要素）があるはずだと想定しています。しかし、サーバーから送られたHTMLには1つもありません。

#### 解決策

意図的にこのようなことをするのはかなりまれですが、サーバーとブラウザで何らかの異なるロジックを実行すれば起こりえます。この種の警告が表示され、自分のコードが原因ではないと思うなら、`<Suspense/>` などのバグである可能性のほうがずっと高いでしょう。GitHubで[issue](https://github.com/leptos-rs/leptos/issues)または[discussion](https://github.com/leptos-rs/leptos/discussions)を作成し、気軽に助けを求めてください。

### 無効なHTMLや境界事例、HTMLとDOMの不一致

サーバーはリクエストにHTMLで応答します。ブラウザはそのHTMLを解析し、Document Object Model（DOM）と呼ばれるツリーに変換します。ハイドレーション中、Leptosはアプリケーションのビューツリーをたどり、要素をハイドレートしてからその子に入り、最初の子をハイドレートし、続いて兄弟へ移動する、という処理を続けます。これは、アプリケーションがサーバーで生成したHTMLツリーが、ブラウザによる解析後のDOMツリーに直接対応することを前提としています。

`view` が作るHTMLツリーとDOMツリーが完全には一致しない場合がいくつかあります。これらはハイドレーションエラーの原因となるため、注意が必要です。

#### 無効なHTML

次はハイドレーションエラーを起こす非常に単純なアプリケーションです。

```rust
#[component]
pub fn App() -> impl IntoView {
    let count = RwSignal::new(0);

    view! {
        <p>
            <div class:blue=move || count.get() == 2>
                 "最初"
            </div>
        </p>
    }
}
```

次のようなエラーメッセージが表示されます。

```
src/app.rs:6:14で定義された要素のハイドレート中に、ハイドレーションエラーが発生しました。

フレームワークはテキストノードを期待していましたが、代わりに次のものが見つかりました：<p></p>

ハイドレーションの不一致は少し前に発生した可能性がありますが、フレームワークが予期しない型のノードを最初に発見したのはここです。
```

（ほとんどのブラウザの開発者ツールでは、その `<p></p>` を右クリックするとDOM内の位置を表示できるので便利です。）

DOMインスペクターを見ると、`<p>` の中に `<div>` があるのではなく、次のようになっています。

```html
<p></p>
<div>最初</div>
<p></p>
```

これは無効なHTMLだからです！ `<div>` を `<p>` の内側に置くことはできません。ブラウザがその `<div>` を解析すると、直前の `<p>` を閉じてから `<div>` を開きます。その後、（対応する開始タグがなくなった）閉じタグ `</p>` を見つけると、新しい空の `<p>` として扱います。

その結果、DOMツリーは期待されるビューツリーと一致しなくなり、ハイドレーションエラーが発生します。

残念ながら、現在のモデルで、全体のコンパイル時間に影響を与えずにビュー内のHTMLが有効かどうかをコンパイル時に保証するのは困難です。当面、このような問題に遭遇したら、出力されたHTMLをバリデーターに通すことを検討してください。（上の例は、実際にW3C HTML Validatorでもエラーになります！）

```admonish info
0.6から0.7へ移行すると、この種のバグに気づくことがあるかもしれません。これはハイドレーションの仕組みが変わったためです。

Leptos 0.1～0.6では、各HTML要素に一意のIDを付け、そのIDを使ってDOMから要素を見つける方法でハイドレーションしていました。Leptos 0.7からはDOMを直接たどり、出会った要素を順にハイドレートするようになりました。この方法は性能特性がはるかに優れています（HTML出力が短くきれいになり、ハイドレーション時間も短縮されます）が、上で示した無効なHTMLや境界事例への耐性は低くなります。ただし、より重要なことに、この方法はハイドレーションに関する*ほかの*多くの境界事例やバグも修正するため、総合的にはフレームワークの堅牢性が向上しています。
```

#### `<tbody>` のない `<table>`

私が把握しているもう1つの境界事例では、*有効な*HTMLからビューツリーとは異なるDOMツリーが生成されます。それが `<table>` です。（ほとんどの）ブラウザはHTMLの `<table>` を解析するとき、記述されているかどうかにかかわらずDOMへ `<tbody>` を挿入します。

```rust
#[component]
pub fn App() -> impl IntoView {
    let count = RwSignal::new(0);

    view! {
        <table>
            <tr>
                <td class:blue=move || count.get() == 0>"最初"</td>
            </tr>
        </table>
    }
}
```

この場合も、ブラウザがビューツリーにはなかった `<tbody>` をDOMツリーに追加したため、ハイドレーションエラーが発生します。

ここでの修正は簡単で、`<tbody>` を追加します。

```rust
#[component]
pub fn App() -> impl IntoView {
    let count = RwSignal::new(0);

    view! {
        <table>
            <tbody>
                <tr>
                    <td class:blue=move || count.get() == 0>"最初"</td>
                </tr>
            </tbody>
        </table>
    }
}
```

（有効なHTML全般をlintするより、この特有の挙動だけなら簡単にlintできるかどうか、今後調べる価値があるでしょう。）

#### 一般的な助言

この種の不一致は厄介なことがあります。デバッグには、一般に次の方法をおすすめします。

1. メッセージ内の要素を右クリックし、フレームワークが最初に問題へ*気づいた*位置を確認します。
2. その位置と上位のDOMをビューツリーと比較し、不一致を探します。余分な要素や、欠けている要素はありませんか？

### クライアント用コードのすべてがサーバーで動くわけではない

ブラウザでリクエストを送るために使い慣れた `gloo-net` のような依存クレートを意気揚々とimportし、サーバーレンダリングするアプリの `create_resource` で使ったとしましょう。

おそらく、すぐに恐ろしいメッセージが表示されます。

```
panicked at 'cannot call wasm-bindgen imported functions on non-wasm targets'
```

これは困りました。

とはいえ、もちろん筋は通っています。ここまで、アプリはクライアントとサーバーの両方で実行される必要があると説明してきました。

#### 解決策

これを避ける方法はいくつかあります。

1. サーバーとクライアントの両方で動くライブラリだけを使います。たとえば [`reqwest`](https://docs.rs/reqwest/latest/reqwest/) は、どちらの環境でもHTTPリクエストに使えます。
2. サーバーとクライアントで異なるライブラリを使い、`#[cfg]` マクロで条件分岐します。（[例はこちら](https://github.com/leptos-rs/leptos/blob/main/examples/hackernews/src/api.rs)です。）
3. クライアント専用コードを `Effect::new` で囲みます。Effectはクライアントでのみ実行されるため、初期レンダリングには不要なブラウザAPIへアクセスする効果的な方法になります。

たとえば、signalが変化するたびにブラウザの `localStorage` へ何かを保存したいとします。

```rust
#[component]
pub fn App() -> impl IntoView {
    use gloo_storage::Storage;
	let storage = gloo_storage::LocalStorage::raw();
	logging::log!("{storage:?}");
}
```

サーバーレンダリング中は `LocalStorage` にアクセスできないため、これはpanicします。

しかし、Effectで囲めば……

```rust
#[component]
pub fn App() -> impl IntoView {
    use gloo_storage::Storage;
    Effect::new(move |_| {
        let storage = gloo_storage::LocalStorage::raw();
		log!("{storage:?}");
    });
}
```

問題ありません！ サーバーではクライアント専用コードを無視して適切にレンダリングし、その後ブラウザでストレージへアクセスしてメッセージを記録します。

### サーバー用コードのすべてがクライアントで動くわけではない

ブラウザで動くWebAssemblyは、かなり制限された環境です。ファイルシステムを利用できず、標準ライブラリなら普段使える多くの機能にもアクセスできません。すべてのcrateをWASM向けにコンパイルできるわけではなく、ましてWASM環境で実行できるとは限りません。

特に、crate `mio` や `core` に含まれるものが見つからないというエラーが表示されることがあります。これは一般に、WASM向けにコンパイルできないものをコンパイルしようとしている兆候です。サーバー専用の依存関係を追加する場合は、`Cargo.toml` で `optional = true` と指定し、`ssr` featureの定義で有効にしてください。（詳しくはテンプレートの `Cargo.toml` ファイルを確認してください。）

何かをサーバーではなくクライアントだけで実行するよう指定するには、[`Effect`](https://docs.rs/leptos/latest/leptos/prelude/struct.Effect.html) を作成できます。では、クライアントではなくサーバーだけで実行するよう指定する方法はあるのでしょうか？

実は、あります。次の章ではserver functionについて詳しく取り上げます。（それまでの間、[こちらのドキュメント](https://docs.rs/leptos/latest/leptos/attr.server.html)も確認できます。）
