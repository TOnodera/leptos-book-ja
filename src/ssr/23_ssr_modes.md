# 非同期レンダリングとSSRの「モード」

同期的なデータだけを使うページをサーバーでレンダリングするのは、かなり単純です。コンポーネントツリーをたどり、各要素をHTML文字列としてレンダリングするだけです。しかし、これにはかなり大きな但し書きがあります。非同期データを含むページ、つまりクライアントでは `<Suspense/>` ノードの下でレンダリングされるようなものをどう扱うべきか、という問いには答えていません。

ページのレンダリングに必要な非同期データを読み込むとき、どうすべきでしょうか？ すべての非同期データが読み込まれるまで待ち、それから全体を一度にレンダリングするのでしょうか？（これを「非同期」レンダリングと呼ぶことにします。）それとも正反対に振り切り、手元にあるHTMLをすぐクライアントへ送り、リソースの読み込みと内容の埋め込みをクライアントに任せるのでしょうか？（これを「同期」レンダリングと呼ぶことにします。）あるいは、両方の長所を備えた中間的な解決策があるのでしょうか？（ヒント：あります。）

ストリーミング音楽を聴いたり、オンラインで動画を見たりしたことがあれば、HTTPがストリーミングに対応していることはご存じでしょう。コンテンツ全体の読み込みを待たず、単一の接続でデータの断片を次々に送れます。また、ブラウザは部分的なHTMLページのレンダリングも非常に得意です。この2つを組み合わせると、**HTMLをストリーミングする**ことでユーザー体験を向上できます。Leptosはこれを、何の設定もせず標準でサポートしています。さらにHTMLのストリーミング方法は1つだけではありません。動画のフレームのように、ページを構成するHTMLの断片を順番にストリーミングすることも、順番を入れ替えてストリーミングすることもできます。

これが何を意味するのか、もう少し詳しく説明しましょう。

Leptosは、非同期データを含むHTMLの主要なレンダリング方法をすべてサポートしています。

1. [同期レンダリング](#同期レンダリング)
1. [非同期レンダリング](#非同期レンダリング)
1. [順序どおりのストリーミング](#順序どおりのストリーミング)
1. [順不同のストリーミング](#順不同のストリーミング)（および部分的にブロックする派生形）

## 同期レンダリング

1. **同期**：すべての `<Suspense/>` の `fallback` を含むHTMLの外枠を配信します。クライアントで `create_local_resource` を使ってデータを読み込み、リソースの読み込みが完了したら `fallback` を置き換えます。

- _長所_：アプリの外枠が非常に速く表示され、TTFB（最初の1バイトが届くまでの時間）が優れています。
- _短所_
  - リソースの読み込みは比較的遅くなります。リクエストを始める前に、JSとWASMの読み込みを待つ必要さえあります。
  - 非同期リソースのデータを `<title>` やその他の `<meta>` タグに含められず、SEOやSNSのリンクプレビューなどに悪影響があります。

サーバーサイドレンダリングを使っているなら、性能の観点から同期モードが本当に望ましいことはほとんどありません。重要な最適化を活用できないためです。サーバーレンダリング中に非同期リソースを読み込めば、サーバー上でデータの読み込みを開始できます。クライアントがHTMLレスポンスを受け取り、JSとWASMを読み込み、そこで初めてリソースが必要だと気づいて読み込みを始めるのを待つ必要はありません。クライアントから最初のリクエストが来た時点で、サーバーレンダリングがリソースの読み込みを始められます。この意味で、サーバーレンダリング中の非同期リソースは、サーバーで読み込みを開始し、クライアントで完了する `Future` のようなものです。リソースがシリアライズ可能である限り、総読み込み時間は必ず短くなります。

> このため `Resource` のデータはシリアライズ可能でなければなりません。また、シリアライズできず、ブラウザ内だけで読み込むべき非同期データには `LocalResource` を使う必要があります。シリアライズ可能なリソースを作れるのにローカルリソースを作ることは、常に性能を低下させます。

2. **`async`**：すべてのリソースをサーバー上で読み込みます。すべてのデータが読み込まれるまで待ってから、一度にHTMLをレンダリングします。

- _長所_：メタタグをより適切に扱えます（`<head>` をレンダリングする前に非同期データが分かるためです）。非同期リソースの読み込みをサーバーで開始するため、**同期**よりも全体の読み込みが速くなります。
- _短所_：読み込み時間／TTFBが遅くなります。クライアントに何かを表示する前に、すべての非同期リソースが読み込まれるのを待つ必要があります。すべての読み込みが終わるまでページは完全に空白です。

## 順序どおりのストリーミング

<video controls>
	<source src="https://github.com/leptos-rs/leptos/blob/main/docs/video/in-order.mov?raw=true" type="video/mp4">
</video>

3. **順序どおりのストリーミング**：コンポーネントツリーをたどり、`<Suspense/>` に出会うまでHTMLをレンダリングします。そこまでに得られたHTMLをストリームの1つの断片として送り、`<Suspense/>` の下で参照されるすべてのリソースが読み込まれるのを待ちます。それをHTMLにレンダリングしてから、次の `<Suspense/>` またはページの末尾に到達するまで処理を続けます。

- _長所_：空白画面のままにするのではなく、データの準備ができる前にも少なくとも_何か_を表示します。
- _短所_
  - `<Suspense/>` ごとに一時停止する必要があるため、同期レンダリング（または順不同のストリーミング）よりも外枠の読み込みが遅くなります。
  - `<Suspense/>` のフォールバック状態を表示できません。
  - ページ全体が読み込まれるまでハイドレーションを開始できないため、一時停止した断片が読み込まれるまで、先に表示された部分も操作できません。

## 順不同のストリーミング

<video controls>
	<source src="https://github.com/leptos-rs/leptos/blob/main/docs/video/out-of-order.mov?raw=true" type="video/mp4">
</video>

4. **順不同のストリーミング**：同期レンダリングと同様に、すべての `<Suspense/>` の `fallback` を含むHTMLの外枠を配信します。ただしデータは**サーバー**で読み込み、解決するたびにクライアントへストリーミングします。`<Suspense/>` ノードのHTMLもストリーミングされ、フォールバックと差し替えられます。

- _長所_：**同期**と**`async`**の長所を兼ね備えます。
  - 同期的な外枠全体を即座に送るため、初期レスポンス／TTFBが高速です。
  - リソースの読み込みをサーバーで開始するため、全体の所要時間も短くなります。
  - 未読み込みのデータ部分を空白にせず、読み込み中のフォールバック状態を表示して動的に置き換えられます。
- _短所_：一時停止した断片を正しい順序で表示するには、JavaScriptが有効でなければなりません。（レンダリング済みの `<Suspense/>` 断片を含む `<template>` タグとともに、小さなJS断片が `<script>` タグでストリーミングされるため、追加のJSファイルを読み込む必要はありません。）

5. **部分的にブロックするストリーミング**：「部分的にブロックする」ストリーミングは、ページに独立した複数の `<Suspense/>` コンポーネントがある場合に役立ちます。ルートに `ssr=SsrMode::PartiallyBlocked` を設定し、ビュー内でブロッキングリソースを参照すると有効になります。いずれかの `<Suspense/>` コンポーネントが1つ以上の「ブロッキングリソース」（後述）を読み取る場合、フォールバックは送信されません。代わりにサーバーはその `<Suspense/>` が解決するまで待ち、サーバー上でフォールバックを解決済みの断片に置き換えます。そのため初期HTMLレスポンスに含まれ、JavaScriptが無効または未対応でも表示されます。ほかの `<Suspense/>` は、デフォルトの `SsrMode::OutOfOrder` と同じように順不同でストリーミングされます。

これはページに複数の `<Suspense/>` があり、一方がもう一方より重要な場合に便利です。ブログ記事とコメント、商品情報とレビューなどを考えてみてください。`<Suspense/>` が1つしかない場合や、すべての `<Suspense/>` がブロッキングリソースを読み取る場合には役立ちません。そのような場合は、より遅い `async` レンダリングになってしまいます。

- _長所_：ユーザーの端末でJavaScriptが無効または未対応でも動作します。
- _短所_
  - 順不同の場合より初期レスポンスが遅くなります。
  - サーバー上の追加処理により、レスポンス全体もわずかに遅くなります。
  - フォールバック状態は表示されません。

## SSRモードを使う

性能特性のバランスが最も優れているため、Leptosのデフォルトは順不同のストリーミングです。しかし、別のモードを選ぶのも非常に簡単です。[`ssr_modes` の例](https://github.com/leptos-rs/leptos/blob/main/examples/ssr_modes/src/app.rs)のように、1つ以上の `<Route/>` コンポーネントへ `ssr` プロパティを追加します。

```rust
<Routes fallback=|| "Not found.">
	// ホームページは、順不同のストリーミングと<Suspense/>で読み込む
	<Route path=path!("") view=HomePage/>

	// 投稿は非同期レンダリングで読み込み、データを読み込んだ「後」に
	// タイトルとメタデータを設定できるようにする
	<Route
		path=path!("/post/:id")
		view=BlogPost
		ssr=SsrMode::Async
	/>
</Routes>
```

複数のネストしたルートを含むパスでは、最も制約の強いモードが使われます。つまり、ネストしたルートが1つでも `async` レンダリングを要求すれば、最初のリクエスト全体が `async` でレンダリングされます。制約が最も強いのは `async`、次が順序どおり、最後が順不同です。（数分考えてみれば、たぶん納得できるでしょう。）

## ブロッキングリソース

ブロッキングリソースは `Resource::new_blocking` で作成できます。ブロッキングリソースも、Rustのほかの `async`／`.await` と同じように非同期で読み込まれます。サーバーのスレッドなどをブロックするわけではありません。代わりに、`<Suspense/>` の下でブロッキングリソースを読み取ると、その `<Suspense/>` が解決するまで、最初の同期的な外枠を含め、HTMLの_ストリーム_が何も返さないようにします。

性能の観点からは理想的ではありません。そのリソースの準備ができるまで、ページの同期的な外枠は一切読み込まれません。しかし何もレンダリングしないことで、`<head>` 内の `<title>` や `<meta>` タグなどを実際のHTMLとして設定できます。これは `async` レンダリングによく似ていますが、大きな違いが1つあります。複数の `<Suspense/>` セクションがある場合、そのうち_1つ_をブロックしながら、別のセクションにはプレースホルダーを表示し、後からストリーミングできます。

たとえばブログ記事を考えてみましょう。SEOやSNSでの共有のために、ブログ記事のタイトルとメタデータは最初のHTMLの `<head>` にぜひ含めたいものです。一方でコメントがまだ読み込まれていなくても気になりません。できるだけ遅延して読み込みたいでしょう。

ブロッキングリソースを使えば、次のように書けます。

```rust
#[component]
pub fn BlogPost() -> impl IntoView {
    let post_data = Resource::new_blocking(/* ブログ記事を読み込む */);
    let comments_data = Resource::new(/* ブログのコメントを読み込む */);
    view! {
        <Suspense fallback=|| ()>
            {move || Suspend::new(async move {
                let data = post_data.await;
                view! {
                    <Title text=data.title/>
                    <Meta name="description" content=data.excerpt/>
                    <article>
                        /* 記事本文をレンダリングする */
                    </article>
                }
            })}
        </Suspense>
        <Suspense fallback=|| "コメントを読み込んでいます...">
            {move || Suspend::new(async move {
                let comments = comments_data.await;
                todo!()
            })}
        </Suspense>
    }
}
```

ブログ記事の本文を含む最初の `<Suspense/>` は、ブロッキングリソースを読み取るためHTMLストリームをブロックします。ブロッキングリソースを待つメタタグやその他のhead要素は、ストリームが送信される前にレンダリングされます。

これを `SsrMode::PartiallyBlocked` を使う次のルート定義と組み合わせると、ブロッキングリソースはサーバー側で完全にレンダリングされ、WebAssemblyやJavaScriptを無効にしているユーザーもアクセスできます。

```rust
<Routes fallback=|| "Not found.">
	// ホームページは、順不同のストリーミングと<Suspense/>で読み込む
	<Route path=path!("") view=HomePage/>

	// 投稿は部分的にブロックするモードで読み込み、重要なデータを
	// 最初のHTMLに含められるようにする
	<Route
		path=path!("/post/:id")
		view=BlogPost
		ssr=SsrMode::PartiallyBlocked
	/>
</Routes>
```

コメントを含む2つ目の `<Suspense/>` はストリームをブロックしません。ブロッキングリソースにより、SEOとユーザー体験のためにページを最適化するうえで必要な能力と粒度を、まさに得ることができました。
